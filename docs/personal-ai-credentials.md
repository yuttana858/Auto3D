# Personal Meshy credentials

This implementation is local and requires deployment and staging validation. It stores a user's Meshy key as an AES-256-GCM encrypted object in the existing private `AUTO3D_LIBRARY_R2` bucket. The object path is separate from user Library paths; account identity is authenticated by the API and bound to the ciphertext as additional authenticated data. The API returns only whether a key is configured. The password field and request necessarily contain the key briefly when the user submits it over HTTPS; it is not stored in browser preferences or returned by the API. Only the server decrypts it for the Meshy request.

Before testing in staging, an administrator must provision `AUTO3D_AI_ENCRYPTION_KEY` as a Cloudflare Pages secret containing a cryptographically random, base64-encoded 32-byte key, and bind the existing private R2 bucket. Generate and enter it through a trusted administrative process; never commit, log, or paste it into chat. Use separate keys and storage for staging and production. Back up and restrict the secret: changing or losing it without a re-encryption procedure makes existing saved keys unreadable. Do not rotate this secret until versioned key management and migration have been implemented and tested. A user can replace or remove their own Meshy key; removal does not revoke it at Meshy. If the shared server key is explicitly enabled, it remains a fallback when a user has no personal key.

Deployment must include a real authenticated user test, cross-account denial, replacement and deletion tests, verification that no request-body logging or public R2 access exposes keys, and provider-key rotation/revocation tests. Task history created with a previous provider key can become inaccessible after replacement. Existing local tests do not establish that production bindings or provider credentials work.
