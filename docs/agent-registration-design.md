# Agent registrations and administration

Status: design only. The connector, the account grant controls, and this preferences entry are not yet deployed. No agent API key issuance, rotation, or per-agent administrator revocation is implemented by this document.

Use the existing per-user OAuth authorization flow for ChatGPT, Claude, and other OAuth-capable MCP hosts. An OAuth client receives its own scoped, revocable grant; users should not copy a reusable Auto3D password or Supabase secret into a harness. Names and harness labels are descriptive, not proof of the client's identity. Do not store bearer tokens in user preferences, browser storage, logs, or the registration record. OAuth authorization codes use PKCE; transport uses HTTPS and tokens remain in the client's credential store.

Where a specific client cannot support OAuth, design a separate optional machine credential only after a threat review. Generate at least 256 random bits server-side, reveal the credential once over an authenticated secure channel, and store only a keyed verifier with its key held in server-side secret management; do not use reversible encryption for the credential verifier. Rotation creates a separate credential, explicitly invalidates the old credential, and records audit events without credential values. Do not equate this optional credential with the Supabase secret used by Auto3D's backend.

The future registration record should associate the verified owner, an opaque registration ID, a user-editable name, a self-reported harness label, scope, creation/expiry/revocation timestamps, and a link to the OAuth grant. Each request must validate the grant, owner account status, scope, and revocation before routing to an explicitly connected session. The UI should show client-reported identities as such and distinguish window readiness from an authorized agent pairing. Avoid exposing token values through commands or agent tools.

Owners need a list of their registrations and actions to connect, rename, and revoke; rotation for OAuth means a fresh authorization followed by revocation of the old grant, not a new manually copied secret. Administrators need a verified admin-only view of registration metadata and individual or account-wide revoke, with audit records, rate limits, account-bound authorization and protection from self-escalation. Existing account disablement is a coarse emergency control that blocks the whole account; it is not a per-agent revoke UI. Staging must validate propagation delays and in-flight behavior before claiming immediate revocation. Agent actions that can reveal or create credentials must not be available to a remote agent.

Implementation requires a versioned owner-scoped database migration, secure server APIs, grant lifecycle integration, admin UI and auditable revocation, account-isolation and cross-user authorization tests, and a real client test. A design for cancellation or termination of an active browser connection must accompany revocation; expiry alone is not immediate revocation.
